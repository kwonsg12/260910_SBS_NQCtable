# NC 근무표 초안 웹앱

승인 권한·관리자 인증을 적용할 때는 [PR3 보안 설정 안내](docs/PR3-security.md)를 먼저 확인하세요.

이 프로젝트는 회사의 8월 NC 근무표를 기반으로 한 로컬 웹 초안입니다.

## 포함 기능

- 8월 기준 4인 근무표 UI
- 일 / 야 / 조 / 비 기본 패턴 유지
- 휴가 신청 폼
- 일근 휴가 시 비번자 대근 자동 처리
- 야/조근 세트 휴가 규칙 반영
- 비번 보장/대근 신청 로그
- 25일 00:00 근무표 확정 기준 안내

## 실행 방법 (사내망 공유 서버, 권장)

여러 PC(직원/담당자)가 같은 근무표·신청 데이터를 보려면 서버로 실행해야 합니다.
Node.js 22.5 이상이 설치되어 있어야 합니다.

1. 이 폴더에서 최초 1회만 의존성을 설치합니다.

```bash
npm install
```

2. 서버를 실행합니다.

```bash
node server.js
```

3. 이 PC의 브라우저는 `http://localhost:8000` 으로, 사내망의 다른 PC는
   `http://<이 PC의 내부 IP>:8000` 으로 접속합니다(서버 실행 시 콘솔에 안내
   문구가 출력됩니다). 데이터는 이 폴더의 `geunmupyo.db`(SQLite)에 저장되며,
   서버를 껐다 켜도 유지됩니다.
4. PC를 재부팅해도 서버가 자동으로 다시 켜지게 하려면 `pm2`(예:
   `npm i -g pm2 pm2-windows-startup` 후 `pm2 start server.js --name geunmupyo`)
   나 `NSSM`으로 Windows 서비스로 등록해두는 것을 권장합니다.

## 서버에서 공개하는 파일

`node server.js`는 `/`, `/index`, `/index.html`과 화면에서 사용하는
`/sbs-logo.png`만 파일로 제공합니다. 승인 링크의 `/?approve=...`도 그대로
사용할 수 있습니다. DB, 로그, 서버 소스, 설정 파일과 의존성 폴더는 파일
다운로드로 제공하지 않습니다. DB 위치와 기존 `/api/state`, `/api/notify`
동작은 동일합니다. API의 사용자 인증·권한 검사는 별도 개선 범위입니다.

새 이미지나 CSS·JS 파일을 화면에서 참조할 때는 `server.js`의 `publicFiles`
목록에도 추가해야 합니다. `*.log` 파일은 Git 추적 대상에서 제외됩니다.

`npm test`로 공개 파일·차단 경로·기존 API를 검증합니다. 테스트는 임시 폴더의
별도 서버와 DB를 사용하며, 실제 근무표 DB나 메일 발송을 사용하지 않습니다.

## 실행 방법 (서버 없이, 이 PC 한 대에서만 테스트할 때)

서버 없이 빠르게 화면만 확인하고 싶다면 기존처럼 정적 파일 서버로도 열 수
있습니다. 이 경우 데이터는 그 브라우저의 localStorage에만 저장되며 다른
PC와 공유되지 않습니다.

```bash
python -m http.server 8000 --bind 127.0.0.1
```

```text
http://localhost:8000/?storage=local
```

## 직원 로그인 (본인 신청 제출·취소)

휴가 신청·비번 보장 신청은 로그인해야 낼 수 있고, 신청자는 로그인한 본인으로
고정됩니다. 본인이 낸 신청(대기 중이거나 이미 확정된 것)은 로그인한 상태에서
언제든 취소할 수 있습니다. 날짜·사유 등 내용을 바꾸려면 취소 후 다시 신청하세요.

1. **로그인 PIN 설정(관리자)** — `설정` 탭 → `근무표 편집` → `직원 구성 편집`에서
   직원별로 `PIN 변경` 버튼을 눌러 6자 이상 PIN을 설정합니다. PIN을 설정하기 전에는
   해당 직원이 로그인할 수 없습니다.
2. **로그인** — 화면 상단 오른쪽에서 이름을 고르고 PIN을 입력해 `직원 로그인`을
   누릅니다. 관리자 인증과 마찬가지로 로그인 상태는 이 브라우저 탭의 메모리에만
   있고 PIN은 저장되지 않으므로, 새로고침하면 다시 로그인해야 합니다.
3. **취소** — `휴가 신청`/`비번 보장 신청` 탭의 신청 내역에서 본인 항목에만 `취소`
   버튼이 보입니다. 취소하면 연결된 대기 중 승인 요청도 함께 정리되어 담당자
   승인함에는 더 이상 나타나지 않습니다.
4. **대근 불가 사유 제출**도 같은 방식으로, `대근 관리·불가사유 신청` 탭에서
   본인에게 배정된 건에 한해 로그인한 상태에서만 제출할 수 있습니다.

## 담당자 승인 워크플로

1. **담당자 등록** — `설정` 탭 → `담당자(승인권자) 관리`에서 이름과 **사내메일 주소**를
   등록합니다. 등록된 담당자 전원이 모든 승인 요청을 받습니다. 승인 PIN을 넣어두면
   승인/반려할 때 확인합니다.
2. **승인이 필요한 건** — 담당자가 1명 이상 등록되어 있으면 아래 세 가지가 승인 대상이 됩니다.
   - 휴가 신청에 따른 대근 배정 (신청 즉시 근무표에 예정으로 반영되고, 반려하면 자동 원복)
   - 비번 보장 월 한도 초과 신청
   - `근무표` 탭의 `이 달 근무표 확정 요청` (승인되면 결재란 `담당` 칸에 승인자 이름과 날짜가 찍힘)
3. **알림 발송** — 요청이 생기면 서버가 담당자에게 사내메일로 승인 링크를 보냅니다.
4. **승인 처리** — 담당자는 메일의 링크(`.../?approve=...`)를 열면 승인함이 바로 열립니다.
   본인을 선택하고 `승인` 또는 `반려`를 누르면 결과가 신청자에게 다시 통보됩니다.

## 메일 설정 (Gmail 공용 계정 → 사내메일)

알림은 메일로만 발송합니다. Gmail 공용 계정으로 담당자·근무자의 사내메일 주소에 보냅니다.
`.env.example`을 `.env`로 복사한 뒤 값을 채우고 서버를 재시작하세요.

1. Gmail 계정에 **2단계 인증**을 켜고 **앱 비밀번호**(16자리)를 발급합니다.
2. `.env`에 `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=465`, `SMTP_SECURE=true`,
   `SMTP_USER`(Gmail 주소), `SMTP_PASS`(앱 비밀번호)를 채웁니다.
3. `npm run digest -- --check`로 로그인이 되는지 확인합니다.

설정이 없으면 발송을 건너뛰고 서버 콘솔에만 기록합니다(나머지 기능은 그대로 동작).
Gmail에서 보낸 메일이 사내 메일 서버에서 스팸으로 분류될 수 있으니, 처음에는 스팸함을
확인하고 필요하면 전산팀에 발신 주소 허용을 요청하세요.

### 일일 요약 메일

매일 `DIGEST_TIME`(기본 18:00, 한국 시간)에 지난 요약 이후 바뀐 내용을 사람별로 모아 보냅니다.
바뀐 내용이 없는 사람에게는 보내지 않습니다.

| 받는 사람 | 내용 |
| --- | --- |
| 근무자 | 내게 새로 배정된 대근(휴가 대근), 대근 배정 해제, 내 휴가·비번 보장 신청의 처리 결과(반려 사유 포함) |
| 담당자(관리자) | 근무자들의 휴가 최종 상태(승인 대기·확정·반려·취소)와 대근 내역, 월 한도를 넘긴 비번 보장 처리 결과, 대근 불가 사유 접수, 승인 대기 건수 |

- **받는 주소**: 근무자는 `설정 → 직원 구성 편집`의 `사내메일`, 담당자는 `담당자(승인권자) 관리`의
  `사내메일`입니다. 주소가 없으면 받지 않고, 같은 주소가 양쪽에 있으면 한 통으로 합쳐 보냅니다.
- 발송에 실패한 사람은 다음 요약 때 밀린 내용까지 함께 받습니다(사람별로 마지막 발송 시각을 기록).
- 서버를 처음 켠 날 발송 시각이 이미 지났다면 그날은 건너뛰고 다음 날부터 보냅니다.
- 수동 실행: `npm run digest`(지금 발송), `npm run digest -- --dry-run`(보내지 않고 내용만 확인).
- 승인 요청 메일(담당자에게 즉시 발송)은 기존대로 동작합니다.

## 커스터마이즈

- 현재 브라우저에서 실행되는 통합 앱은 `index.html`입니다. 설정 탭의 관리자 설정에서 근무자 목록과 적용 시작일을 입력합니다.
- 근무자 변경은 적용 시작일 이후의 근무표에만 반영됩니다. 관리자 인증은 후속 서버 연동 단계에서 추가합니다.
- 오늘 이전 근무표는 날짜별 스냅샷을 우선 사용하므로 일반적인 근무자 변경으로 과거 값이 다시 계산되지 않습니다.
- 설정 탭의 관리자 수동 근무 편집에서 직원별 날짜의 근무 유형을 `일 / 야 / 조 / O`로 지정할 수 있습니다. 과거 날짜를 바꾸려면 수정 사유가 필요합니다.
- 관리자 수동 근무 편집에서 연도와 월을 선택해 해당 월을 직접 수정할 수 있습니다.
- 수동 근무 편집의 `직원 구성 편집`에서 이름 수정, 직원 추가·삭제, 적용 시작일·종료일을 행 단위로 관리할 수 있습니다. 더 이상 근무자 목록을 줄글로 다시 입력할 필요가 없습니다.
- 신규 인원의 **적응기간**은 `신규 투입 · 로테이션 시작점`의 `적응기간 일괄 채우기`로 지정합니다. 반복 값에 `일`처럼 하나만 넣으면 매일 같은 근무, `야,조`처럼 쉼표로 넣으면 그 순서대로 반복되며, 채운 뒤 표에서 개별 수정도 가능합니다. `근무표 변경 적용`을 눌러야 저장됩니다.
- **단독근무 투입**은 `로테이션 시작점`으로 지정합니다. 투입일과 그 날 시작할 근무(일/야/조/O)만 정하면 이후는 `일→야→조→O` 4일 주기로 무한 자동 반복되며, 날짜별로 미리 채워둘 필요가 없습니다. `기존 직원 자리 이어받기`를 고르면 기준 직원이 그 날 맡았을 근무를 자동으로 가져옵니다. 14일 미리보기에서 다른 직원과 근무가 겹치는 날은 ⚠로 표시되지만(증원 시 정상일 수 있어) 차단하지는 않습니다.
- 로테이션 시작점은 등록 즉시 반영되고 `해제`로 되돌릴 수 있습니다. 등록·해제 시점에 지난 날짜는 스냅샷으로 고정되어 과거 근무표는 다시 계산되지 않습니다.
- 직원별 시작일·종료일 범위와 표시값으로 `경조휴가`, `교육`, `출장` 같은 여러 날의 병합 셀을 만들 수 있습니다. 병합된 값은 실제 근무표에서 하나의 가운데 정렬 셀로 표시됩니다.
- 병합 범위가 겹치면 저장이 차단되며, 저장된 병합 범위는 해제할 수 있습니다. 최근 근무표 변경은 되돌릴 수 있습니다.
- 근무표 수정 기능 자체는 아직 인증 없이 사용할 수 있습니다(변경 기록은 감사 기록으로 남습니다). 승인/반려에만 담당자 선택과 선택적 PIN 확인이 걸려 있으며, 수정 기능까지 포함한 관리자 로그인은 다음 단계 과제입니다.

## 주요 규칙 반영

- 25일 00시 이전에 제출된 휴가 계획은 자동 확정
- 비번 보장 신청은 월 2~3회 허용 가정
- 일근 휴가: 비번자 대근 확정
- 야근/조근: 세트 휴가 처리
- 미리 비번 보장을 못 잡은 경우 사유 제출

## 여러 PC에서 저장할 때

다른 사람이 먼저 저장한 경우, 나중에 저장하는 화면에는 충돌 안내가 나옵니다.
먼저 저장한 사람의 내용을 덮어쓰지 않습니다. 자동으로 두 변경을 합치지는 않으므로
필요한 내용을 확인한 뒤 최신 근무표에서 다시 수정해주세요.

- 화면 상단에서 저장 대기·저장 중·저장 완료·실패·충돌을 확인할 수 있습니다.
- 연결에 실패해도 이 브라우저 전용 저장으로 자동 전환하지 않습니다.
- 미저장 변경은 현재 탭의 임시 보관소에 남아 같은 탭을 새로고침할 때 복구됩니다.
  브라우저가 탭을 복원하지 않으면 남아 있지 않을 수 있습니다. 탭을 닫기 전에는
  '내 변경 내려받기'로 JSON 파일을 보관할 수 있습니다. 파일 자동 가져오기는 제공하지 않습니다.
- 충돌 시 '최신 근무표 불러오기'를 누르면 현재 변경을 버릴지 먼저 묻습니다.
  '계속 편집'으로 취소할 수 있고, 서버 조회에 실패하면 현재 내용은 유지됩니다.
- 통신 실패는 '다시 시도'로 재저장할 수 있습니다. 응답만 유실된 경우에는
  실제 저장 여부를 안전하게 판단하기 위해 충돌 안내가 나올 수도 있습니다.
- 근무표의 '새로고침'도 서버 최신 데이터와 휴일 정보를 다시 조회합니다.
- 최초 서버 조회에 실패하면 편집을 막고 재시도를 안내합니다.
  빈 서버에 이전 브라우저 데이터를 자동으로 올리지 않습니다.

서버 없이 쓰려면 HTML 파일을 직접 열거나 위의 `?storage=local` 주소를 사용하세요.
이 모드에서는 화면 상단에 '이 브라우저에서만 사용 중'이라고 표시하며 서버 저장·알림은 요청하지 않습니다.
공유 모드와 로컬 모드는 자동으로 서로 전환되지 않습니다.

### 서버 업데이트와 테스트

기존 SQLite 데이터는 서버 실행 시 저장 버전 정보만 자동으로 추가하며 보존합니다.
서버를 재시작한 뒤 사용 중인 브라우저도 새로 열어주세요. 예전 화면의 버전 없는 저장 요청은
덮어쓰기 방지를 위해 거절됩니다. 서버 코드를 이전 버전으로 되돌리면 충돌 방지 기능도 사라집니다.

`npm test`로 동시 저장·통신 실패·초안 복구·기존 DB 이관을 검증합니다.
실제 근무표 DB나 메일 발송은 사용하지 않습니다.
API 인증·권한 및 저장 후 알림 발송은 별도 개선 범위입니다.
