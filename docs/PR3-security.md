# PR3: 승인 권한과 PIN 보호

## 달라지는 사용 방법

- 직원은 기존처럼 신청합니다. 휴가 승인, 초과 비번 보장 승인, 월 확정은 승인함에서 담당자를 선택하고 PIN을 입력해야 처리됩니다.
- 담당 범위에 들어 있지 않은 사람은 승인할 수 없습니다. 담당 범위가 일치하는 사람이 없을 때 전원에게 권한을 주던 동작도 없앴습니다.
- 설정·직원·수동 근무표·담당자 명부 변경은 화면 상단 **관리자 인증** 후 가능합니다. 인증은 15분 또는 서버 재시작까지 유효하고, 화면을 새로고침하면 다시 인증해야 합니다.
- 담당자는 새로 등록할 때 6자 이상 PIN이 필요합니다. 기존 담당자의 PIN이 없거나 바꿔야 하면 관리자 인증 후 **PIN 변경**을 누릅니다.
- 저장 실패는 상단에 표시합니다. 관리자 인증이 만료됐다면 다시 인증하고 **저장 재시도**를 누르세요. PIN 변경 입력은 브라우저 저장소에 남기지 않으므로 저장 전 새로고침하면 다시 입력해야 합니다.

## 운영자가 처음 적용할 때

1. 서버를 종료하고 기존 DB와 .env를 별도로 백업합니다. 백업에는 기존 비밀값이 있을 수 있으므로 서버 운영자만 접근하도록 보관합니다.
2. 서버 .env에 임의의 충분히 긴 **ADMIN_PASSWORD(12자 이상)** 를 설정하고 서버를 시작합니다. 실제 값을 Git에 올리지 않습니다.
3. 기존 DB에 들어 있던 담당자 PIN은 시작 시 자동으로 소금값을 붙인 scrypt 해시로 옮깁니다. 기존 PIN은 그대로 사용할 수 있습니다. 일반 근무표 JSON과 그 안의 버전 기록에서는 PIN·관리자 PIN·SMTP 비밀번호·카카오 키를 제거합니다. 화면에 저장했던 관리자 PIN은 인증 수단으로 사용하지 않습니다.
4. 기존 SMTP 설정은 서버의 SMTP_HOST / SMTP_USER / SMTP_PASS를 계속 사용합니다. 화면에만 적어 두었던 비밀값이 필요했다면 백업을 참고해 .env에 설정합니다.
5. 새 저장소라면 관리자 인증으로 기본 데이터를 먼저 저장합니다. 이후 담당자를 등록하고 직원들이 신청하면 됩니다. file://로 연 화면에서는 서버 승인·관리자 기능을 사용할 수 없습니다.
6. 여러 PC에서 PIN을 입력하는 실제 사용 환경은 HTTPS로 연결합니다. 같은 서버 PC에서 동작하는 HTTPS 프록시의 전달 프로토콜을 지원합니다. 기존 HTTP 자체에는 전송 암호화가 없습니다.

## 서버에서 막는 우회

- /api/state로 승인 결과·기존 신청·배정 담당자·월 확정을 위조하거나 지울 수 없습니다. 관리자도 승인 처리는 전용 API를 사용해야 합니다.
- 신규 신청은 승인 대기 여부, 비번 보장 한도, 연결된 승인 요청과 담당 범위를 서버가 확인합니다.
- PIN 변경과 상태 저장을 SQLite 트랜잭션으로 묶어 저장이 거절됐는데 PIN만 바뀌는 일을 방지합니다.
- PIN/관리자 인증을 5회 틀리면 해당 인증 대상은 15분 동안 제한합니다.
- DB·서버 코드·환경설정 파일을 HTTP로 내려받지 못하게 합니다. PR1 없이 이 PR만 적용해도 PIN 해시가 담긴 DB를 내려받을 수 없습니다.
- 입력 내용은 HTML로 실행되지 않게 출력하고 인라인 이벤트 속성을 없앴습니다. CSP도 추가해 등록되지 않은 스크립트와 HTML 이벤트 속성 실행을 차단합니다.
- 알림 API는 서버에 저장된 승인 대기 건과 담당자 주소만 사용합니다. 같은 승인 건은 1분에 한 번만 요청할 수 있습니다. 일반 안내는 화면 알림에 남기며, 실제 메일/카카오 발송은 저장된 승인 요청에 한정합니다.

## 범위와 다른 PR

이 PR은 원본 master에서 독립적으로 작성했습니다. PR1·PR2를 먼저 머지할 필요는 없습니다.

PR1의 파일 공개 제한은 이 보안 변경만 선택해도 안전하도록 필요한 부분을 동일하게 포함했습니다. PR2와는 저장 API와 화면 저장 코드가 겹치므로 함께 머지할 때 충돌 해결 및 통합 검증이 필요합니다. 이 PR의 권한 검사와 PIN 전달을 유지하면서 PR2의 baseRevision, 충돌 처리, 초안 복구를 연결해야 합니다. 자동 병합 가능하다는 의미의 독립 PR은 아닙니다.

직원 개인 로그인은 이번 범위에 포함하지 않습니다. 공유 근무표 열람과 일반 신청은 사내 사용자에게 열려 있으며, 개별 신청자의 신원을 인증하는 시스템은 아닙니다. 일정 계산·변경 이력 개선과 알림 배달 보장은 후속 PR 범위입니다.

기존 의존성에 대한 npm audit 결과는 3건(높음 1건, 보통 2건)입니다. nodemailer와 express/qs의 버전 업데이트는 이번 변경에 포함하지 않았으며, 별도 업데이트와 발송 호환성 검증이 필요합니다.

## 검증

npm test는 별도 임시 DB와 별도 포트의 서버를 사용합니다. 실제 메일·카카오 발송은 끕니다.

기존 PIN 이동과 비밀값 비노출, 파일 다운로드 차단, 다른 담당자/틀린 PIN 거절, 중복 승인, 승인 결과 위조, 관리자 권한, PIN 변경 롤백, 인증 시도 제한, 초과 보장/월 확정, 알림 수신자 위조, HTML 출력, 잘못된 입력을 확인합니다.
